# TG-Group 产品需求与开发规范

> 本文档是 TG-Group 的需求基线。开发、修复、测试和部署均须遵守。需求未确认前不得擅自删减、替换或宣称完成。

## 1. 产品定位与目标

TG-Group 是面向多用户、多 Telegram Bot、多 Telegram 群组的完整群管理平台。目标是覆盖成熟 Telegram 群管机器人常见的完整功能，而不是只实现少数基础功能。功能必须拆解为可配置、可执行、可查询、可审计、可测试的具体条目。一个模块有页面或开关，不代表该模块已完成。

平台支持多个用户。每个用户可绑定多个自己拥有的群管 Bot；每个 Bot 可管理多个群组；每个群组有独立配置。租户数据必须严格隔离。

## 2. 注册入口与账号体系

### 2.1 网站注册
用户可在网站注册账号、登录、购买套餐，之后绑定自己的 Telegram 群管 Bot Token。网站注册用户也可以稍后绑定 Telegram ID。

### 2.2 Telegram 注册管理机器人
平台可配置一个平台统一的注册管理 Bot。用户点击 /start 后通过菜单交互注册。平台自动读取 Telegram 用户 ID，检查唯一性并创建平台账号，自动绑定该 Telegram ID，生成随机初始密码，并发送网站地址、用户 ID 和初始密码。用户可在 Bot 中查看账号、套餐、机器人等信息，购买套餐后提交自己的群管 Bot Token，平台验证后绑定。

### 2.3 两种入口完全等价
两种入口只是注册和操作入口不同，不存在用户类型差异。账号、套餐、权限、机器人、群组、规则和订单全部共享同一套后端数据与业务逻辑。任何用户均可使用网站和 Telegram 两端。

### 2.4 唯一性与安全
- 一个 Telegram ID 最多绑定一个平台账号。
- 一个平台账号最多绑定一个 Telegram ID。
- 一个用户可以绑定多个群管 Bot。
- 重复注册/绑定必须拒绝并给出明确原因。
- 初始密码应随机生成；建议首次登录强制修改密码（作为安全建议，正式上线前由项目所有者确认）。
- 密码只存安全哈希；Token/API Key 等凭证加密存储并脱敏展示；禁止写入日志。

## 3. 多租户、机器人与群组
- 用户可新增、验证、启用、停用、解绑、轮换多个 Bot Token。
- 绑定时验证 Token、Bot 身份和 API 连通性。
- 一个 Bot 可管理多个群；每群独立设置完整规则。
- 支持群列表、Bot 状态、群权限状态、配置模板、规则复制、批量配置和跨群总览。
- 所有查询与写入均按租户及资源归属校验，防止跨用户访问。
- Bot 缺少管理员权限或 Telegram API 不支持某操作时，界面应明确提示。

## 4. 群管理功能矩阵（持续扩展，不是穷尽清单）

以下每个功能域都必须继续拆成具体功能点和验收用例。不能以只完成一两种模式就标记整个模块完成。

1. **入群验证**：数字验证码、字母验证码、数学题、按钮验证、图片验证码、人机验证、CAP 验证、超时、重试、失败动作、验证豁免、验证状态和日志。
2. **关注/加入验证**：关注指定频道、加入指定群组、多个频道/群组、成员资格检查、未完成限制、重新检查和失效处理。
3. **欢迎/离群通知**：文本、图片、视频、媒体、变量占位符、按钮、个性化消息、欢迎规则、离群通知与清理。
4. **反广告**：网址、短链接、域名、广告关键词、推广文案、邀请链接、外部导流和例外规则。
5. **反垃圾/反刷屏**：重复消息、频率限制、洪水攻击、无意义内容、恶意账号、异常行为和速率阈值。
6. **成员管理**：警告、禁言、解除禁言、限制发言权限、踢出、封禁、解封、批量操作、处罚历史和申诉流程。
7. **管理员系统**：管理员角色、细粒度权限、操作授权、危险操作二次确认、管理员操作日志。
8. **关键词与敏感词**：词库、正则/匹配策略、触发条件、自动回复、删除、警告、禁言、踢出、封禁、优先级和例外。
9. **自动处罚**：警告次数、递进处罚、时间窗口、处罚时长、自动撤回/禁言/踢出/封禁、人工复核。
10. **消息与媒体限制**：文本、图片、视频、GIF、贴纸、语音、音频、文件、投票、联系人、位置、转发等消息类型控制。
11. **群组保护**：防机器人、防批量入群、防恶意拉人、防异常加入/退出、防恶意管理员操作。
12. **信誉与名单**：用户信誉、积分/等级（可配置启用）、黑名单、白名单、豁免名单、违规历史。
13. **自动回复**：关键词回复、精确/模糊匹配、随机回复、菜单回复、定时回复和变量。
14. **定时任务**：定时公告、提醒、消息发送、自动清理、规则任务、任务状态与失败重试。
15. **统计分析**：成员总量与变化、活跃度、消息量、进退群、处罚统计、规则命中和管理报表。
16. **日志审计**：入群、退群、消息处理、处罚、管理员操作、配置变更、Bot 状态、异常和失败原因。
17. **自定义规则引擎**：触发条件、动作、过滤器、例外条件、优先级、冲突处理、启停、测试和执行记录。
18. **多群管理**：每群独立配置、配置模板、复制、批量调整、跨群搜索和统一总览。
19. **竞品补充项**：持续研究成熟群管机器人，补齐上述分类未覆盖的能力；必须记录来源、Telegram API 限制及验收条件。

## 5. 网站与 Telegram Bot 双端等价

- 每项已交付功能必须同时提供网站端和 Telegram Bot 端的完整配置、启停、查询和管理能力。
- 不允许网站可配置而 Bot 端只能查看，也不允许 Bot 端能配置而网站端不能配置。
- 两端使用同一后端服务、权限模型和数据源，配置变更及时同步。
- Telegram 日常管理通过 Inline Keyboard、菜单、分页、分步输入、确认/取消等交互完成，不要求用户记忆管理命令。/start 可作为入口。
- Bot 端必须支持复杂规则的分步配置、输入校验、返回/取消、分页、搜索、权限检查和危险操作确认。
- 对 Telegram Bot API 无法实现的能力，明确标注限制和替代方案，不能虚构支持。

## 6. 套餐与支付

- 注册后可查看套餐。
- 网站注册用户在网站购买套餐后绑定 Bot；Telegram 注册用户在注册管理 Bot 内购买套餐后绑定 Bot。
- 两种入口共用订单、支付、套餐和授权系统。
- 支付方式：USDT、EPUSDT、GMPay。
- 后台配置尽量只需服务商接口/网站地址、商户 ID、密钥；不要求管理员手工填写回调 URL。
- 平台自动适配订单创建、支付状态核验和授权开通。若服务商强制要求 Webhook，由平台自动生成接收端点并提供必要配置说明。
- 不得假定所有支付商都能无回调自动确认，必须以官方 API 文档和实际联调为准。
- 必须验证签名、商户、订单号、金额、币种、支付状态；实现幂等、超时、过期订单、重复回调和对账。
- 支付成功后自动开通套餐，不需要人工审核。
- 网络、链、确认数、手续费、退款等未确认规则不得擅自假定，实施前列为待确认事项。

## 7. CAP 人机验证

- 使用 CAP 官方新版：https://capjs.js.org/
- 禁止旧版 API、SDK、配置格式和旧示例。
- 开发前核对官方当前文档与版本；前后端使用同一新版规范。
- 服务端必须完成验证结果校验，覆盖启用 CAP 的注册/登录等流程。
- 覆盖失败、超时、重复提交、服务不可用等异常路径；完成端到端测试。
- 不得擅自替换为 Turnstile 或其他 CAPTCHA。

## 8. 赞助商模块

- 支持平台级赞助商和单群赞助商。
- 字段：赞助商名称、图片/头像、介绍、跳转地址、按钮文案/展示文本、展示位置、排序、开始/结束时间、启用/暂停/删除。
- 支持多个赞助商列表或轮播展示。
- 支持按群独立配置、全局配置、展示统计和点击统计；统计精度及 Telegram 可追踪范围需按实际能力说明。
- 网站和 Telegram Bot 两端均可管理，配置共享同步。
- 可通过 Telegram 消息及 Inline Keyboard URL 按钮等能力展示；不得将平台自建赞助商功能混称为 Telegram 官方 Sponsored Messages。

## 9. 用户自配置 AI 智能审核

- 每个用户自行选择 AI 服务商、填写自己的 API Key、选择模型和审核策略；平台管理员不统一代配用户密钥。
- 提供常见服务商适配入口：OpenAI、Anthropic、Google Gemini、DeepSeek、阿里云 Qwen、Moonshot/Kimi、Mistral、Groq、OpenRouter、Together AI、Fireworks AI 等。实际接入以供应商当前官方 API 能力为准。
- 支持自定义 OpenAI-compatible API Base URL。
- 输入 API Key 后可点击自动获取模型列表并交互选择，不要求手工输入模型名称。
- 不得假设所有供应商都支持同一种模型列表 API；使用 provider-specific adapter。模型能力需区分文本、视觉、文件输入、工具调用等，不能虚报。
- 审核任务：文本、广告、诈骗、钓鱼链接、辱骂、骚扰、色情、暴力等；图片/文件/文档审核按模型能力实现。
- 文档解析至少评估 TXT、PDF、DOCX；需明确文件大小、格式和解析限制。
- 支持删除消息、警告、禁言、踢出、封禁；动作需受 Bot 权限约束。
- 支持置信度阈值、人工复核、白名单/黑名单、例外用户、规则自定义、审核范围。
- API 不可用时按用户配置 fallback 策略执行，不得假报成功。
- 记录审核结果、原因、模型、置信度、触发规则、执行动作及结果。
- 提供调用次数、Token 用量和费用估算；用户 API Key 加密存储。
- 网站与 Telegram Bot 两端均可配置服务商、模型、审核策略和处罚规则，且配置同步。

## 10. 技术栈与 UI 强制规范

- Web 前端采用 React + TypeScript，并严格使用 shadcn/ui 官方组件体系。
- 所有 UI 控件必须来自 shadcn/ui 官方组件或由官方组件组合；不得混入其他 UI 组件库，不得私自编写一套替代组件库或自造基础控件。
- 使用 shadcn/ui 官方 CLI 添加/管理组件，保留可追踪的官方组件源码和依赖版本。
- 业务代码、状态管理、API 适配、数据模型、服务端逻辑和必要的业务样式仍需开发；“全部用框架组件”约束 UI 组件，不是禁止业务逻辑代码。
- 自定义业务界面只能组合官方组件；新增 UI 变更须在开发日志注明使用的 shadcn/ui 组件。
- 后端语言由项目所有者明确指定为 Go（Golang）。
- Go HTTP 框架/路由库、模块边界和异步任务实现须经架构评估后确定，不得未经评估随意引入。
- 数据基础设施采用 PostgreSQL 和 Redis。

## 11. Docker 部署与交付

- 最终交付 Docker Compose 一键部署。
- 服务器不需要安装开发环境，不需要在服务器编译前端或后端源码。
- 应用镜像在云端 CI 构建、测试并推送镜像仓库；服务器只拉取预构建镜像并启动。
- 自动启动应用、PostgreSQL、Redis；自动初始化数据库和必要配置。
- 自动选择一个未占用的五位数宿主机 Web 端口，排除常见端口；选择结果持久化，重启保持不变，并处理并发占用。
- 启动成功输出访问地址和管理员初始登录信息。
- 默认管理员账号 admin，初始密码 123456；建议首次登录强制修改密码（作为安全建议，正式上线前由项目所有者确认）。
- 部署脚本应检查 Docker/Compose、端口、磁盘和网络，失败需明确报错，不得假报成功。
- CI、镜像仓库和最终部署域名等细节后续确认。

## 12. 质量与验收标准

每个具体功能必须具备：
1. 可用的数据模型和后端逻辑；
2. 网站端完整交互；
3. Telegram Bot 端完整交互；
4. 权限与租户隔离；
5. 异常处理、状态反馈和日志；
6. 自动化或明确的手工验收用例；
7. Telegram API/供应商限制说明（如适用）。

只有代码实现、构建通过、相关测试通过、双端流程验证通过、文档同步后，才可标记完成。页面存在、按钮可点或接口返回 200 均不代表功能完成。未实现/部分实现/受限/待验证必须如实标记。
