# TG-Group 开发计划与当前状态

> **状态口径（2026-11-27，main 分支）**：本节为唯一有效的当前状态摘要；下方较早日期的阶段记录属于历史日志，若与本节冲突，以本节及最新开发日志为准。功能只有在实现、自动化测试、CI、双端验收和文档同步均有证据后才能标记完成。

## 当前技术基线

- Web：React + TypeScript + Vite。
- UI：严格使用 shadcn/ui 官方组件源码与官方 CLI；禁止替换框架或混入其他 UI 组件库。
- Backend：Go 1.23+，标准库 net/http，pgx/v5。
- 数据：PostgreSQL；Redis 已列入本地 Compose，但尚未接入 Go 业务服务。
- 交付：GitHub Actions 云端构建 GHCR 镜像；服务器拉取预构建镜像，Web 端口固定 18680。
- 默认分支：main；本项目按现有主分支连续开发，不另建开发分支。

## 下一阶段执行顺序

1. **P0：警告递进处罚可靠性**——已提交持久化后台重试、指数退避、processing 超时回收和启动 worker；继续验证 SQL 迁移、并发领取、失败退避、崩溃恢复及真实 Telegram 至少一次执行边界。
2. **P0：自动处罚测试**——补服务层测试、PostgreSQL 集成测试、并发/重复执行/失败恢复/隔离测试，并运行 CI。
3. **P0：成员管理闭环**——已完成服务端分页；继续处罚历史分页、搜索/批量操作，并明确 Telegram API 成员枚举限制。
4. **P1：群管矩阵**——按需求基线逐项拆分功能、网站交互、Telegram Inline Keyboard、后端执行和验收。
5. **P1：双端一致性**——逐项检查同一业务服务、权限和数据，不以菜单占位视为完成。
6. **P2：套餐/订单/支付**——先核实各服务商官方协议，再开发 provider adapter 和幂等状态机。
7. **P2：赞助商与 AI**——按需求基线实施，密钥加密、模型能力核验、失败保护。
8. **最终验收**——CAP 公网、Telegram 真实群组、支付沙箱、部署备份恢复及完整需求矩阵。

## 开发完成定义

每项功能都必须具备：数据库/服务端逻辑、租户权限校验、网站交互、Telegram 端交互（若适用）、异常处理与审计、自动化测试、CI 证据、真实环境验收记录及同步文档。未满足的项目保持“部分实现/待验证/未完成”。
